# Three computers can automate content creation

**Yes: your three-computer arrangement can run an automated content workflow, but the machines alone do not make it fully autonomous.** A small always-on computer can schedule work, track jobs, call online AI services, and submit posts; your Ryzen PC can handle rendering and supported local AI jobs when it is online; and your MacBook can remain your daily workstation. To run without your intervention, the system still needs separately configured service credentials, persistent storage, a supported media-hosting and publishing route, retries, monitoring, and a tested fallback when the Ryzen PC is off. Your current Buffer and GitHub connections are a useful foundation, but they are not yet an end-to-end server pipeline. **CAD $50/month is plausible for an automation-heavy, mostly text-and-image pilot; daily generated 3D video is not proven viable within that ceiling.** These findings are a November 1, 2026 snapshot; availability and pricing should be rechecked before setup or spending.

## Let the small server coordinate and the Ryzen PC render

The **always-on computer** runs a single self-hosted n8n instance, maintains a durable job ledger, holds encrypted credentials, schedules research and posts, and receives job completion results. It must remain powered on, awake, connected to the internet, and configured to restart the service after interruptions. Your **MacBook** is the control and review screen; the server must not depend on the MacBook's desktop app or browser session. The **Ryzen 7 5800X PC**, with its 16 GB system RAM, RTX 3060 Ti, 500 GB SSD and 2 TB hard drive, is the optional heavy worker for FFmpeg video assembly, encoding, and compatible local AI experiments. Its 3060 Ti has **8 GB VRAM**; actual local model compatibility, speed and quality must be tested rather than assumed ([NVIDIA specifications](https://www.nvidia.com/en-us/geforce/graphics-cards/30-series/rtx-3060-3060ti/); [FFmpeg documentation](https://ffmpeg.org/ffmpeg-all.html)).

For the server, a **used Linux mini PC or laptop with 8 GB RAM, two or more CPU cores and an SSD** is a practical target, not a guarantee or a universal requirement. n8n's particular Docker Compose guide with its AI-code sandbox identifies **4 GB RAM and two vCPUs** for that setup; Windows Docker Desktop lists **8 GB RAM** and hardware virtualization among its prerequisites ([n8n Compose setup](https://docs.n8n.io/deploy/host-n8n/install-options/install-using-docker-compose/); [Docker Windows requirements](https://docs.docker.com/desktop/setup/install/windows-install/)). Storage needs depend on video retention, so a 120 GB SSD is a reasonable convenience rather than a formal minimum. Compare actual machines and prices before buying.

The scheduler should assign a durable job ID and place work requiring the GPU PC into a queue. A small worker on that PC checks for work, downloads the required inputs, renders, then returns the result and status. **If the PC is off, local GPU and FFmpeg jobs wait** unless we separately configure and test wake-on-LAN or a cloud fallback. Cloud model calls can still run from the small server if the internet, credentials and service are available. One coordinator and one simple worker are enough for a pilot; n8n's full distributed queue mode adds Redis and storage considerations that are not yet justified ([n8n queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode/)).

Both machines should communicate over the home network or an authenticated private VPN. Do not expose an unprotected n8n dashboard to the internet. Keep service credentials in n8n's credential store, keep private conversation exports out of GitHub, and back up the n8n data and encryption key together; losing that key can make stored credentials unusable. Set bounded retries, file-size limits, job timeouts and error reporting. A remote server needs its **own authorized connections**; the existing Mac-side OAuth sessions do not transfer automatically ([n8n security guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/); [n8n data persistence](https://docs.n8n.io/deploy/host-n8n/install-options/install-with-docker/)).

## APIs connect the AIs, and video sets the budget

In the proposed workflow, a scheduled trigger collects eligible sources, a model proposes a sourced story, another optionally critiques it, a visual service or local worker creates media, and the publisher schedules it. The services do not need to open chat windows or manually copy messages between applications. n8n documents integrations for [Anthropic](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.lmchatanthropic/) and [OpenAI credentials](https://docs.n8n.io/integrations/builtin/credentials/openai/); the particular credentials and model access must be provisioned and tested for this server. **Using all three models on every story is optional:** compare results and only add calls that improve quality enough to justify the cost and delays.

The owner's Gemini Pro, ChatGPT and Claude chat subscriptions do not by themselves demonstrate that their API usage is included. Anthropic and OpenAI describe chat and API billing as separate, although some eligible plans or promotions can have credits; Google API projects have separate free and paid tiers, with model and account eligibility requirements. The actual account plans and credits remain unknown. Never ask the owner to paste credentials into chat ([Anthropic](https://support.anthropic.com/en/articles/9876003-i-subscribe-to-a-paid-claude-ai-plan-why-do-i-have-to-pay-separately-for-api-usage-on-console); [OpenAI](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform); [Google](https://ai.google.dev/gemini-api/docs/billing/)). Eligible Claude plans can sign into Claude Code; whether a particular unattended scripted workflow is allowed and workable under this owner's entitlement needs verification ([Claude Code](https://docs.anthropic.com/en/docs/claude-code/getting-started)).

**The cartoon page is the expensive uncertainty.** Google's current listed Gemini Omni Flash video API price is approximately **US $0.10 per second of 720p output**, paid tier, with input charged separately. At the Bank of Canada's October 30 illustrative USD/CAD rate of 1.396, 30 days × 16 generated seconds costs **US $48 or approximately CAD $67** for output alone. Twelve 16-second Reels cost **US $19.20 or approximately CAD $26.80** for output alone; if half the seconds are regenerated, that increases to approximately CAD $40.20. These examples exclude input, failed or extra takes beyond the scenario, other model calls, tax, conversion fees, electricity and subscription charges. Your card exchange rate will differ. The existing subscription may already consume some of the CAD $50 ceiling, which has not yet been decided ([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing); [Bank of Canada](https://www.bankofcanada.ca/rates/exchange/daily-exchange-rates-lookup/?dF=2026-10-17&dT=2026-10-31&lP=lookup_daily_exchange_rates_2017.php&rangeType=dates&sR=2017-01-01&se=FXUSDCAD)).

The current Gemini video guide reports the retirement of `veo-3.1-*-preview` Gemini Developer API endpoints on October 22, 2026, so do not build on older snippets without checking current model availability. Image-to-video and references can help, but **consistent characters and a publishable clip on the first attempt have not been proven** for this couple ([Gemini video guide](https://ai.google.dev/gemini-api/docs/video); [Gemini Omni guide](https://ai.google.dev/gemini-api/docs/omni)). First run a small number of scenes, count all takes and billable seconds, and inspect actual outputs. A stylized still-image and motion-compositing approach may cost less, but its audience appeal and quality must also be tested.

Use a monthly budget ledger with a conservative reserve for each job, a maximum number of paid attempts, and a stop condition before requesting additional work. Provider alerts and spend caps are helpful but **are not guaranteed hard limits**: Google notes that project caps can lag and some in-flight workloads can exceed them. Avoid enabling paid billing or buying credits until the total budget and account ownership are settled ([Google billing limits](https://ai.google.dev/gemini-api/docs/billing/)).

## Buffer and public media need server-specific access

The existing setup already includes a connected **Trywise AI Instagram channel in Buffer**, one published carousel, and a public `trywise-media` GitHub repository that successfully supplied images to a Buffer draft. The owner has provided `@thecozy.2` as the new page handle, but the second page's professional status and Buffer connection have not been verified. The first unattended daily publishing run has not been proven. Existing Codex automations and the Mac-side Python prototype must be migrated or replaced and tested; they do not become an always-on server merely because a second machine exists.

Buffer's published free plan currently lists **three channels and ten queued posts per channel**, enough in principle for two Instagram accounts and one YouTube channel, subject to account eligibility and live plan verification. Buffer documents automatic publishing for connected professional Instagram accounts through Instagram login, for which a linked Facebook Page is not generally required, though particular features differ ([Buffer pricing](https://buffer.com/pricing); [Buffer Instagram connection](https://support.buffer.com/en-us/articles/connecting-your-instagram-account-to-buffer-n9Ad6veXsu)). Buffer's n8n guide specifies a **Buffer API key** for its MCP Client integration. A working Codex OAuth session is not proof that the new server already has that credential; determine whether an appropriate server key is available and store it securely ([Buffer n8n guide](https://developers.buffer.com/guides/integrations/n8n.html)).

Buffer's API expects publicly reachable media URLs instead of uploading local binary files itself; video assets must remain available through publication. The GitHub repository has worked for small still images, but ordinary Git blocks files above **100 MiB** and warns above 50 MiB. A reliable public video-hosting route with appropriate limits and costs must therefore be chosen and tested; do not assume a GitHub image test proves video delivery. Record the destination, content hash, schedule and Buffer ID, and verify the final provider status and post link. When a submission result is ambiguous, reconcile with existing posts before retrying to prevent duplicates ([Buffer media hosting](https://developers.buffer.com/guides/hosting-media); [GitHub file limits](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)).

If YouTube is added later, its account authorization, API project quota, upload visibility and actual outcome need a separate test; documentation on unverified-project visibility has changed over time. YouTube also judges original value across a channel: assembling automatically generated templates does not by itself establish monetization eligibility ([YouTube upload endpoint](https://developers.google.com/youtube/data/reference/rest/v3/videos/insert); [YouTube monetization policies](https://support.google.com/youtube/answer/1311392?hl=en)).

## Build one verified daily run before scaling

Start by agreeing whether existing subscriptions and electricity are inside the CAD $50 monthly limit and identifying the server machine and operating system. Prepare the small server with a supported Docker Compose setup, private access, persistent storage, backups and the correct Edmonton timezone. Connect one eligible free-tier model and the existing Trywise Buffer channel, then run a simple non-public test that passes a structured story from one model to another and saves the result. Add providers only after their credentials, quotas and economics are understood.

Next connect the Ryzen PC as an intermittent worker and verify the queue survives the PC being off, restarts, and duplicate job delivery. Use an original five-slide carousel or a short pilot cartoon as the first production test; preserve a character reference sheet and inspect several generated takes for consistency. Verify actual cost, upload and destination before expanding. Finally, run one complete scheduled cycle without manual handoffs and independently check the resulting post. A working workflow should resume after restart, stop safely on exhausted quota or failed media validation, keep public media available until posting, and report failures instead of silently losing or repeating work.

The **machine architecture is feasible; reliable unattended operation remains an engineering and testing outcome**, not an established property of the existing setup. A particularly useful early decision is whether quality and budget support the desired cartoon frequency. If they do not, the same server can continue daily researched AI posts while producing fewer, better cartoon Reels without blocking either page.
