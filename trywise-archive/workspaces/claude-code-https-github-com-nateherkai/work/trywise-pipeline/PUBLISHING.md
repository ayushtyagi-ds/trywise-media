# Buffer send prototype (not live-tested)

`buffer_publish.py` can enqueue a specific, explicitly reviewed manifest into Buffer, but it is not connected, scheduled or verified with an actual Buffer account. No social post has been created by the tests. It creates a queued Buffer item (not proof Instagram published) using the documented createPost API: https://developers.buffer.com/examples/create-image-post.html . It does not upload media, check Instagram eligibility, retrieve metrics, or verify source claims and rights.

IMPORTANT: A digest represents the caption, channel ID, and image URLs, not the remote image bytes. A mutable media URL could change after review or before publication. Use stable, immutable versioned URLs whose images have been independently checked. A digest does not itself prove a person reviewed anything. Public URLs make images public before publishing. Buffer says media must remain publicly accessible until post time: https://developers.buffer.com/guides/hosting-media.html .

1. Use a dedicated test Buffer account, securely authorize the intended channel, and review provider permissions and cost. Buffer API keys are account-wide; do not post keys to chat or commit them to Git. https://developers.buffer.com/guides/authentication.html
2. Create a UTF-8 JSON manifest with `channel_id`, `caption`, `image_urls`. Inspect caption, every final image at its final URL, permissions, intended channel and factual claims. A prior local carousel approval is not a Buffer submission approval: it does not bind destination channel or hosted URLs.
3. `python3 buffer_publish.py preview manifest.json` prints the exact approved fields and SHA-256 digest; it does not make a network request. Review it. This digest binds channel, caption, URL text and image order, not image bytes.
4. Only after explicit approval, and having confirmed stable public URLs, configure `BUFFER_API_KEY` securely in the running environment. Never pass the key in command arguments. Then explicitly invoke:
   `python3 buffer_publish.py send manifest.json --db /path/to/persistent-ledger.sqlite3 --approved-digest APPROVED_SHA256 --send --ack-public-media`
5. Inspect `python3 buffer_publish.py status --db /path/to/persistent-ledger.sqlite3 --digest APPROVED_SHA256` and verify the result in Buffer and on Instagram. `confirmed` means Buffer returned a post ID, not actual publication. `rejected`, `unknown`, or a stale `pending` record must never be retried blindly. Search the Buffer queue and reconcile before any further action.

The SQLite ledger reserves each digest and commits before transmission, so concurrent processes sharing the same durable ledger cannot send the same digest twice. A crash before transmission leaves a conservative pending state; a timeout, malformed response, or uncertain failure leaves unknown. **No auto retry, override, or ledger reset is provided.** The application returns exit status 2 on rejected/unknown, nonzero on other errors. The ledger must be persisted and shared across every runner, invocation and restart; using separate/deleted databases bypasses protection. Different content or URLs yield a different digest and may lead to duplicate publishing despite looking similar. Buffer documents that write requests lack idempotency protection: https://developers.buffer.com/guides/efficient-api-usage.html .

Before production: validate the request schema, carousel support, queue policy, actual stable asset handling, returned status lifecycle and idempotency with an authorized test account; security review and durable backup/reconciliation workflow remain required. The provider/Instagram may reject posts or change APIs. No unattended writes should be enabled until real end-to-end tests pass.
